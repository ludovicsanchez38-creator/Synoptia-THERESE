# LOT78 : frontière Seatbelt de Chromium sur macOS

Revue de sources seulement, le 9 octobre 2026. Aucun lancement, changement de profil ou admission. Les liens Chromium visent `main` et **ne démontrent pas la parité** avec la copie QA de Chrome 154.0.8037.99 utilisée par ROOT15.

## Ce que montrent les sources

1. Le modèle Chromium ordinaire considère le **browser parent privilégié et non sandboxé par Chromium**, tandis que les renderers et autres helpers reçoivent des sandboxes propres au type de processus. La [table de plateformes, M128](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/security/process-sandboxes-by-platform.md) et le [guide de revue IPC](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/security/ipc-reviews.md) l'énoncent. Cela ne décrit pas la surcouche G1 locale. Dans [`chrome_exe_main_mac.cc`, lignes 169–181](https://chromium.googlesource.com/chromium/src/+/main/chrome/app/chrome_exe_main_mac.cc#169), l'appel à `SeatbeltExecServer::CreateFromArguments` est compilé seulement pour `HELPER_EXECUTABLE`, avant chargement du Framework, et non pour l'exécutable browser.

2. Dans [`child_process_launcher_helper_mac.cc`, lignes 122–207](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/child_process_launcher_helper_mac.cc#122), le browser choisit le type de sandbox du helper, sérialise sa politique (compilée ou source), lui transmet un FD et le switch `--seatbelt-client=`, lance l'enfant via `base::LaunchProcess`, puis envoie le profil sur le tube **après** le lancement. Sur macOS, [`base::LaunchProcess` appelle `posix_spawnp`, lignes 403–412](https://chromium.googlesource.com/chromium/src/base/+/master/process/launch_mac.cc#403) ; ce chemin montré n'est pas un `fork` de type zygote Linux.

3. [`seatbelt_exec.h`, lignes 60–93](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/sandbox/mac/seatbelt_exec.h#60) et [`seatbelt_exec.cc`, lignes 148–184](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/sandbox/mac/seatbelt_exec.cc#148) définissent `sandbox_required` : il vaut vrai si **le processus receveur** porte ce switch. Le serveur lit alors le profil sérialisé et l'applique. Ce booléen ne certifie ni ne protège le browser parent. Le [document de conception macOS](https://chromium.googlesource.com/chromium/src/+/HEAD/sandbox/mac/seatbelt_sandbox_design.md) confirme que le Helper applique sa politique avant `ChromeMain`/le Framework.

4. Le [README du sandbox macOS Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/sandbox/mac/README.md) distingue Seatbelt d'App Sandbox et indique qu'une politique Seatbelt borne le processus **et ses descendants**. Dans ROOT15, G1 applique [`sandbox-exec` au browser Chrome, avec `chrome.sb` deny-default](/private/tmp/therese-c17-wrapper-canary-9c1f04187dd24519b220372284a739c9/g1/runtime_session.py) ; les [stderr Chrome ROOT15](/private/tmp/therese-c17-wrapper-canary-9c1f04187dd24519b220372284a739c9/auxiliary/aux-chrome-rpc-all-runtime_ui-visual_capture-network_capture/stderr.log) montrent `Failed to initialize sandbox`, `Operation not permitted`, puis GPU inutilisable. La source amont explique un **chemin plausible** de conflit de politiques successives ; elle ne prouve pas à elle seule la cause exacte dans le binaire Chrome 154 ou ce noyau.

## Conséquence pour « politique initiale unique »

Dans les sources examinées, il n'y a **pas de surface documentée** pour imposer un profil G1 arbitraire au browser tout en demandant aux descendants d'appliquer normalement leur propre profil Chromium. Ce n'est pas une preuve d'impossibilité générale. Un browser root-owned lancé hors G1 garderait des contrôles d'identité, de CDP et de fermeture, mais perdrait la limite noyau G1 deny-default du browser et son héritage sur les descendants ; les sandboxes internes des helpers ne la remplaceraient pas. Le broker Chromium décrit dans le README autorise des demandes contrôlées d'un helper vers le browser privilégié, pas une sandbox du browser. Une intégration de politique dans les sources/build Chromium, ou une autre frontière prouvée équivalente, serait un changement d'architecture et d'autorité, pas un simple paramètre de lancement démontré ici.

Inconnus explicites : source exacte du build Chrome 154.0.8037.99 QA ; entitlements effectifs de ce binaire ; opération Seatbelt exacte ayant renvoyé `EPERM` dans ROOT15 ; interaction précise entre les politiques de ce build et macOS 26.6.2. Les deux sondes synthétiques LOT76/77 ne qualifient pas cette combinaison ni l'héritage des helpers Chromium.
