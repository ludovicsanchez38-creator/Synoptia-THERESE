## Lot A - Le Board délibère avec les modèles au sommet

### Constats CORRIGÉS par le challenge (contre le code réel)
- `get_llm_service_for_provider` calcule `model_override or user_model or
  default_model` (llm.py:1062) : sans override explicite, un utilisateur
  configuré OpenAI/gpt-5.5 donnerait gpt-5.5 à un conseiller. **Le Board
  doit passer `model_override=frontier(provider)` + `effort_override="max"`**
  - le comportement du helper ne change PAS (les agents l'utilisent,
  agents/runtime.py:58).
- Le « clamp global max→high » de la V1 était FAUX : le code transmet déjà
  `max` tel quel aux gpt-5.6*, plafonne SEULEMENT grok-4.5 à high, et
  n'envoie RIEN aux gpt-5.5/5.4 (verrouillé par
  tests/test_provider_effort.py:66). **gpt-5.5 reste sans paramètre.**
- `claude-fable-5` est déjà dans `_EFFORT_PREFIXES` ; `claude-opus-5` est
  absent de `_EFFORT_PREFIXES` ET de `_NO_SAMPLING_PREFIXES` (le corps lui
  enverrait temperature et zéro effort).
- `MistralProvider` n'hérite PAS d'OpenAIProvider : boucle HTTP et parseur
  propres (mistral.py:121), qui supposent une string - le correctif chunks
  est local à Mistral. `StreamEvent` n'a pas d'évènement thinking : les
  chunks thinking sont IGNORÉS proprement. Mistral force `stream: true` :
  pas de test « non-stream », tester le normaliseur pur + variantes SSE
  (y compris le changement de forme en cours de flux).
- Il y a QUATRE tables de modèles codées en dur dans llm.py (491 config
  principale, 555 repli par clé, 630 circuit breaker, 1016 helper), pas
  deux.

### Design A1

1. **Catalogue neutre** `app/services/modeles_catalogue.py` - AUCUN import
   de llm.py (pas de cycle). Par fournisseur : enum, variables d'env,
   contexte, liste ordonnée (tête = frontier). Par modèle : politique
   d'effort à TROIS états (`non_envoye` | `transmis_tel_quel` |
   `traduit(valeur)`) + `max_tokens_recommande` éventuel. Importe
   `LLMProvider` depuis `providers.base`, JAMAIS llm.py. Consommé par les
   QUATRE tables de llm.py + `_available_models_for` de config.py (qui
   garde son contrat `list[str]` - contrat frontend config.ts:212 et test
   d'ordre test_modeles_disponibles.py:72). OpenRouter et Ollama gardent
   leur découverte dynamique.

   **Le catalogue est la SEULE source de la politique d'effort**, via un
   RÉSOLVEUR UNIQUE `resoudre_effort(modele, effort_demande) ->
   effort_resolu` appelé par TOUTE création de `LLMConfig` - les TROIS
   chemins : `_default_config`, `get_llm_service_for_provider`, ET
   `POST /config/llm` (config.py:1339, qui installe la config à chaud -
   sans lui, le réglage serait ignoré jusqu'au redémarrage ; test exigé :
   POST puis chat immédiat). Les configs créées par les tables de repli
   (llm.py:555) et du circuit breaker (llm.py:630) passent aussi par le
   résolveur. Les providers émettent `config.effort_resolu` dans LEUR
   syntaxe SANS table locale : `_EFFORT_SUPPORTED` (openai.py:66) et
   `_EFFORT_PREFIXES` (anthropic.py) DISPARAISSENT - l'effort d'opus-5
   vit au CATALOGUE, anthropic.py ne conserve que `_NO_SAMPLING_PREFIXES`
   (qui gagne claude-opus-5). **Ollama** : les modèles sont dynamiques,
   inconnus du catalogue - le résolveur renvoie « transmis tel quel » et
   le provider GARDE sa dégradation gracieuse existante (`think` + retry
   sans think, sentinel `_THINK_UNSUPPORTED`).
2. **Board** : `get_llm_service_for_provider(p, model_override=frontier(p),
   effort_override="max")` - nouveau paramètre `effort_override`, défaut
   None = comportement actuel intact. Test avec des préférences utilisateur
   volontairement non frontier (gpt-5.5) : le conseiller reçoit quand même
   gpt-5.6-sol.
3. **Anthropic** : l'effort d'opus-5 s'inscrit au CATALOGUE (la table
   `_EFFORT_PREFIXES` disparaît, cf. résolveur unique) ; `claude-opus-5`
   s'ajoute à `_NO_SAMPLING_PREFIXES`, la seule table locale conservée
   (exclusion du sampling CONFIRMÉE à la source par le contre-challenge -
   doc extended-thinking-models).
   `max_tokens` : mécanisme UNIQUE - nouveau paramètre
   `max_tokens_override` de `get_llm_service_for_provider`, posé sur
   `LLMConfig.max_tokens` AVANT `prepare_context()` ; la réserve de
   `prepare_context` (llm.py:739, 4096 codé) lit désormais la config
   effective. `stream_response()` ne change pas de signature : c'est la
   CONFIG qui porte la valeur. Le Board applique le
   `max_tokens_recommande` du catalogue (64000 pour claude-opus-5) ; le
   chat garde son défaut.
4. **Mistral** : normaliseur local `str | list -> str` (concat des
   chunks `text`) pour l'AFFICHAGE (StreamEvent) - testé pur + sur les
   deux formes de `delta.content`. Pour la boucle à OUTILS multi-tours :
   TRANSPORT FIGÉ de bout en bout : le brut est le JUMEAU EXACT du
   texte du tour, il suit le même chemin que `assistant_content` /
   `continued_content` (le ToolTurn de chat.py:3007 décrit le tour
   COURANT via le PARAMÈTRE `assistant_content` - le brut fait pareil,
   aucun décalage de tour possible) :
   1. `StreamEvent` (base.py:123) gagne un champ optionnel
      `assistant_content_brut: Any | None = None` ; MistralProvider le
      pose sur l'évènement `tool_call` qu'il émet quand le content du
      tour était une liste de chunks (thinking compris) ;
   2. le producteur du chat capte ce champ à la réception du premier
      `tool_call` et le passe à `_execute_tools_and_continue` via un
      NOUVEAU paramètre jumeau `assistant_content_brut: Any | None =
      None` (chat.py:2621, à côté d'`assistant_content`) ;
   3. dans `_execute_tools_and_continue` : le `ToolTurn` construit à
      chat.py:3007 reçoit `assistant_content_brut` DU PARAMÈTRE (le tour
      courant, comme `assistant_content`) ; et la boucle de continuation
      capte une variable jumelle `continued_content_brut` sur
      l'évènement `tool_call` du flux de continuation, transmise à
      l'appel récursif - symétrie stricte avec `continued_content` ;
   4. `ToolTurn` (base.py:110) gagne le champ optionnel
      `assistant_content_brut` ; au rejeu (`continue_with_tool_results`
      / prior_turns), MistralProvider le préfère quand présent (la doc
      Mistral exige le message assistant complet ; mistral.py:181
      reconstruit le texte seul - à corriger) ; les autres providers
      l'ignorent (None).
   Tests : multi-tours avec DEUX tours d'outils (le rejeu du tour 1
   contient la liste brute du tour 1, celui du tour 2 la sienne - le
   décalage d'un tour serait rouge), deux chats concurrents, provider
   non-Mistral à champ None. Aucune trace de thinking n'est affichée.
5. **Grok** : extraire dans OpenAIProvider une tentative réutilisable
   `_stream_request(request_body)` qui laisse remonter `HTTPStatusError` ;
   GrokProvider fait UNE seconde tentative si 400 ET `reasoning_effort`
   présent, corps copié sans le champ. Tests : les deux corps émis, aucune
   duplication de texte ni d'appels d'outils.
6. **Synthèse** : inchangée (LLM principal de l'utilisateur, board.py:483).
7. **Contrat reformulé** : « le frontier de chaque fournisseur EFFECTIVEMENT
   configuré ; sinon repli EXPLICITE sur le service principal (visible dans
   actual_provider, comportement existant) ; jamais de repli de MODÈLE
   silencieux au sein d'un fournisseur. »

### Design A2 - détection de dérive (dernier lot)

- Accroche : début de `BoardService.deliberate()` (board.py:194), avant la
  recherche web. Au plus une sonde par jour (date Europe/Paris), verrou
  asyncio, timeout 5 s par fournisseur, uniquement les fournisseurs à clé
  configurée. Après redémarrage : re-sonde à la première délibération.
- Sondes : GET /models OpenAI-compatible (openai, grok, mistral),
  GET /v1/models (Anthropic), GET /v1beta/models (Gemini) - contrats
  vérifiés à l'implémentation.
- **État partagé** : `BoardService` est recréé à chaque requête - l'état
  de sonde vit au niveau MODULE de services/board.py (`_etat_catalogue:
  dict[str, bool | None]` + verrou asyncio + date de dernière sonde
  module-level), comme les registres du chantier 0.47.
- **Sondes PARALLÈLES** (asyncio.gather), timeout global 6 s - jamais
  cinq timeouts en série avant le premier chunk.
- **Définition de « dérive »** (stricte, testable) : le frontier du
  catalogue est ABSENT de la liste renvoyée par le fournisseur. Endpoint
  indisponible = PAS une dérive (log, drapeau inchangé, re-tentative le
  lendemain). Alias déplacé / nouveau flagship = éditorial, hors sonde.
- **États** de `modele_deprecie` (champ optionnel par AdvisorInfo,
  additif, board.ts:84) : absent/null = non sondé, false = vérifié
  présent, true = absent de la liste.
- **Chunk** : `BoardDeliberationChunk` existant (type + content),
  type="catalogue_status", content = JSON compact
  {"providers": {"openai": true, ...}} - même mécanique que
  synthesis_chunk. Émis seulement quand une dérive est connue. JAMAIS de
  bascule de modèle.
