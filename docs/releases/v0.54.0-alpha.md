## La revue : huit passes sur un seul outil

`invoice_totals` (lot B3) a été repris **huit fois** avant publication. C'est le
seul lot qui produit un chiffre sur de l'argent, et c'est là que se concentre
tout l'enseignement de cette release.

| Passe | Relecteur | Défaut trouvé |
|---|---|---|
| 1 | Soso | Additionne les devises : 1 000 EUR + 1 000 USD → `2000`, avec un simple drapeau à côté |
| 2 | Soso | Une facture sans devise fait passer un mélange pour une devise unique (base migrée, pas neuve) |
| 3 | Soso | Arrondis divergents (2,11 contre 2,10) ; retard de -5 jours ; facture négative qualifiée d'avoir |
| 4 | Grok | Le total peut être négatif sous un nom qui promet une recette |
| 5 | Grok | Le gel du scalaire laisse le nombre vivre dans le dictionnaire, que le prompt ordonne de lire |
| 5 | Soso | Sur-correction : `null` rendu là où un chiffre exact existe |
| 6 | Soso | Le contrat annoncé au modèle contredit le code (« positif » exclut zéro) |
| 6 | Grok | Une devise qui s'annule fait taire les autres |
| 7 | moi | Le drapeau contredit le scalaire ; le compteur contredit la liste |
| 7 | Grok | La note contredit le total ; `retard_par_devise` sans le filtre de l'encours |
| 8 | Grok | Le gate du retard lit un ensemble filtré, un négatif s'additionne quand même |

**Six de ces défauts sont des « jumeaux »** : une règle posée sur un champ et
non balayée sur les autres. Les trois derniers sont nés de mes propres
correctifs, pas de la conception.

Bascule de nature à la sixième passe : les quatre premières trouvaient un
**montant faux annoncé comme certain**, les dernières un **montant juste tu par
excès de prudence**. La famille dangereuse s'est fermée avant la seconde.

## Ce qui a été appris, et qui vaut plus que le correctif

Une recherche faite **après** coup — et qui aurait dû être faite avant d'écrire
le lot C : l'arithmétique monétaire multi-devises est un problème résolu.

- Stocker en `float` est la cause racine d'au moins trois des huit passes. Le
  domaine recommande `Decimal`, ou mieux, des **entiers en plus petite unité**
  (1940 centimes plutôt que 19,40 €).
- Un type `Money` qui **refuse** d'additionner deux devises différentes rend le
  défaut de la passe 1 impossible à écrire, au lieu d'une chose à découvrir.
- Le motif Money de Fowler traite la divergence entre la somme du détail et le
  total par une méthode `allocate()` qui distribue le reliquat.

Aujourd'hui, `subtotal_ht`, `total_ttc` et `unit_price_ht` sont des `float` dans
le modèle, et aucune bibliothèque monétaire n'est installée. La correction n'est
donc pas dans `invoice_totals` : elle est une couche en dessous. C'est le
chantier F, ouvert par cette release.

Un défaut de gate corrigé au passage : la suite n'était pas hermétique aux clés
IA de la machine. `_has_any_llm_key` sortait en `True` depuis `os.environ` avant
d'atteindre le code que trois tests sabotent ; avec une clé posée — donc sur la
plupart des postes — un test échouait en ressemblant à une régression du
produit. **Un gate dont le résultat dépend de l'environnement n'est pas un
gate.**

## Dette nommée, non corrigée

- `InvoiceLineRequest` n'impose aucune borne : une ligne de facture négative
  reste acceptée par le backend (le garde-fou n'existe que côté écran).
- Le statut « Accepté » est proposé sur le formulaire d'une facture : la choisir
  la fait sortir de l'encours.
- `retard_ttc` est brut, avant avoirs : il peut dépasser l'encours. C'est
  documenté dans le contrat de l'outil, pas corrigé — allouer un avoir à une
  facture précise serait inventer une écriture comptable.
- Le total sans LLM sur le panneau Facturation, annoncé au design de B3, n'a pas
  été livré.
- `maintenant` est en UTC naïf face à des échéances civiles : une pièce peut
  basculer dans le retard autour de minuit.
- Le mode cabinet n'a pas d'écran, il s'active par l'API.
- `PUT /api/config/preferences/{key}` est inatteignable en HTTP (« Field
  required » sur toutes les formes essayées, pour toute préférence).
