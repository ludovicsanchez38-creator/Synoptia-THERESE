# Release v0.42.0-alpha — 31/07/2026

> **Première tranche du chantier de conception 0.42.** Le plan couvre
> 18 suggestions accumulées depuis la 0.40 ; cette release en livre les
> fondations (jalons J0 et J1) plus deux morceaux de J2 et J4. Les autres
> suivront. C'est dit ici pour que personne ne cherche dans cette version des
> fonctions qui n'y sont pas encore.

## Le fil rouge

Les triages Discord ont accumulé 19 suggestions de conception, presque toutes de
Dr_logic. Elles disent toutes la même chose sous des formes différentes :
**l'utilisateur ne sait pas ce que la machine fait, ni ce qu'elle a reçu, ni ce
qu'elle sait faire.**

L'exploration du code a montré que le chantier est autant du **raccordement** que
de la construction : l'infrastructure existait souvent déjà, sans être branchée.

## Ce que cette version corrige

### L'accueil de la coque était inerte (J0a)

En 0.41.3, les raccourcis de l'accueil — actions rapides, conversations
récentes, panneaux du jour — appelaient `useNavigationStore.setView(...)`. Or la
coque n'observait pas ce store : **zéro occurrence** dans
`ConversationCanvasPrototype.tsx`. Cliquer ne faisait donc rien du tout.

La coque suit désormais une source de navigation unique, verrouillée par un gate
de parité **par source d'action** : chaque bouton, commande déterministe et
raccourci clavier doit produire un changement visible. Le gate part du registre
d'actions entier, avec exemptions nommées — sa première version, filtrée sur une
liste de vues, ratait silencieusement toute action hors de cette liste.

### Le bouton Arrêter ne prévenait pas le serveur (J1b)

`POST /api/chat/cancel/{id}` existait depuis longtemps. **Aucun code d'interface
ne l'appelait** : le bouton se contentait d'un abandon local. La réponse
s'arrêtait à l'écran pendant que le fournisseur continuait de produire — et de
facturer.

Pire, le drapeau d'annulation n'était consulté qu'**après** production d'un
morceau : quand le fournisseur est lent ou bloqué, c'est-à-dire exactement quand
on veut arrêter, la boucle restait suspendue et l'annulation n'avait aucun effet.

Corrigé sur quatre plans, chacun trouvé par une passe de revue successive :

1. production et surveillance mises en concurrence, le producteur est fermé ;
2. **déconnexion du client** (fenêtre fermée, réseau coupé) : fermer le
   producteur pendant que sa tâche tournait levait une erreur qui empêchait le
   nettoyage du registre — l'entrée fuyait et le producteur tournait dans le
   vide ;
3. **écritures tardives** : la réponse pouvait être enregistrée après le clic et
   réapparaître au rechargement ;
4. **la boucle d'outils** ignorait complètement l'annulation. Elle pouvait créer
   un contact, un projet, ou écrire un document sur le disque **après** la
   demande d'arrêt, sans rien à l'écran pour l'expliquer.

Le suivi des tokens, lui, reste compté sur une génération annulée : ils ont été
réellement consommés, les escamoter fausserait le coût affiché.

### Le mode classic est retiré (J0b)

L'ancienne interface vivait en parallèle depuis la 0.41.0 comme filet de secours.
Elle est supprimée : la coque est désormais l'unique interface. Ce que le classic
portait seul a été repris — préférence « ignorer l'accueil », liens profonds,
pont de recette `window.__therese`, pile Échap unifiée.

L'état de connexion, qui ne vivait que dans la surface de chat, remonte dans
l'en-tête : un utilisateur dans CRM, Fichiers ou Factures voit enfin quand le
backend tombe.

### Socle des traitements longs (J1a)

Le dépôt contenait **quatre registres d'annulation** en mémoire, sans lien entre
eux et aux mécaniques non interchangeables. Ils sont désormais enveloppés
derrière un adaptateur commun, avec deux couches : une table durable
(`processing_tasks`) et un registre runtime.

Deux invariants tenus :

- `cancel_requested` n'est **pas** `cancelled`. Annoncer un arrêt qu'on n'a pas
  obtenu ferait croire à l'utilisateur qu'un traitement s'est arrêté alors qu'il
  consomme encore ;
- une tâche restée « en cours » après un arrêt brutal devient `interrupted` au
  démarrage suivant. Sans ce ménage, une mission d'Atelier bloquait toute
  nouvelle mission sans plus pouvoir être annulée.

### Le cloisonnement documentaire (J2, partiel)

Le filtrage par périmètre existait des **deux** côtés — champs en base, filtre
dans Qdrant — mais aucun payload indexé n'écrivait les clés correspondantes.
Le mécanisme ne pouvait donc rien filtrer, et le contexte du chat cherchait sans
aucune cloison : un document rattaché à un projet pouvait ressortir dans une
conversation étrangère. Pour un assistant qui agrège des données de plusieurs
clients, c'est un défaut de confidentialité.

Le périmètre est maintenant écrit par un **constructeur unique**, utilisé par
l'indexation comme par l'upload de pièce jointe de projet — les deux
construisaient auparavant leur payload séparément, ce qui garantissait la
divergence.

Les documents indexés avant cette version n'ont pas de périmètre : ils sont
traités comme globaux. **Aucune réindexation, aucune purge** : un document qui
disparaît est plus grave qu'un document trop visible.

**Reste à faire** : brancher le filtre côté chat. Cela suppose un rattachement
conversation ↔ projet qui n'existe pas encore.

### `/aide` (J4, partiel)

Le bouton Aide envoyait littéralement le texte `/aide`, que le parseur ne
reconnaissait pas : la demande partait au modèle, qui improvisait une réponse sur
les capacités de l'application. La commande est désormais reconnue et répond
localement, à partir de l'aide dérivée du code.

## Vérification

**Trois passes de revue adversariale (Codex), toutes trois en NO-GO**, chacune
avec reproduction par exécution plutôt que par lecture.

| Passe | Findings | Issue |
|---|---|---|
| 1 | 10 (2 bloquants, 5 majeurs, 3 mineurs) | tous corrigés |
| 2 | 3 régressions **dans la remédiation elle-même** | toutes corrigées |
| 3 | 1 défaut de fond (boucle d'outils) | corrigé |

Trois défauts trouvés dans mon propre travail méritent d'être notés :

- le périmètre documentaire n'était écrit que sur un chemin, pas sur celui
  qu'emprunte réellement l'utilisateur ;
- 344 Mo de cache mypy avaient été commités par un `git add -A` (retirés, la
  branche n'étant pas poussée ; `.mypy_cache/` désormais ignoré) ;
- **trois tests étaient creux**, dont un qui *verrouillait* un bug. Le gate de
  parité était tautologique ; sa réécriture a immédiatement trouvé une action
  que l'ancienne version ne voyait pas.

## Dette et limites assumées

- **Le filtre de périmètre n'est pas branché côté chat.** La fuite décrite
  ci-dessus existe donc encore en usage réel : le travail livré la rend
  corrigeable, il ne la corrige pas.
- **Le raccordement de la reprise des tâches au démarrage n'est pas couvert par
  un test.** Un test exécutant le vrai `lifespan` a été écrit puis retiré : sa
  sortie ferme la base partagée et cassait 329 tests. La requête, elle, est
  testée.
- **Une extraction de fichier déjà lancée va à son terme** (`run_in_threadpool`
  est en `abandon_on_cancel=False`).
- Compatibilité rompue : les anciens liens `?prompt=...`. Les liens actuels
  passent par `sessionStorage`.
